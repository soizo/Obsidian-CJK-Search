异体字来源、Unicode 字段语义、日／朝覆盖与分发许可的详细调查见 [汉字异体与编码兼容数据源调查](variant-data-sources.md)。

## 项目现状

工作目录当前无产品代码和 Git 仓库。需求是独立 Obsidian 插件，增强原生全库搜索，输入框始终保留原始输入，结果由原生搜索展示。

## OpenCC 初步边界

来源：[OpenCC 官方 README](https://github.com/BYVoid/OpenCC/blob/master/README.md)，本轮通过 GitHub API 读取默认分支；选型时须固定版本并重新验证。

- 官方介绍区分简繁、地区异体字和地区习惯用词转换，不提供一般意义上的跨语言翻译。
- 预设配置列出简繁、台湾、香港方向；地区词汇另有配置。
- README 将日文新旧字体转换描述为有限支持，并将 `t2jp`、`jp2t` 标为探索性研究、不建议用于生产环境。不能据此承诺日本汉字标准完整覆盖。
- 该预设配置列表未列朝鲜半岛专用配置。这不代表字典中没有 `真／眞` 等个别对应，也不能证明具备完整朝鲜半岛覆盖；必须继续核查实际字典和权威标准。
- 官方将 `opencc-js`、`opencc-wasm` 列在官方／推荐移植之下；尚未选择运行时或验证其数据与上游一致性。

## 已确认的产品边界

- 必须支持桌面、iOS 和 Android；移动端不是可选附加项。最低系统及 Obsidian 版本尚未确定。
- 数据来源已确定仅保留 Unicode 官方数据＋OpenCC 官方字符字典；不引入其他字表。按来源、许可、版本及映射语义选取数据，具体选择见专题调查。
- 互搜范围包括汉字写法、同一字符的不同码位表示，以及所需的标点变体；不扩展地区习惯用词或跨语言翻译。例如 `鼠标／鼠標` 属于范围内，`鼠标／滑鼠` 不属于范围内。
- 用户明确提出康熙部首与对应汉字、顿号与日语顿号。标点的具体码位仍需明确，不能仅按语言名称判断。
- 用户选择「默认限定，可开启全量」：默认处理东亚文字相关的汉字、对应部首、兼容汉字及确认的标点变体；提供可选的全量 Unicode 兼容匹配，启用后也允许 `①／1`、`²／2`、`Ａ／A` 等互搜。默认精确字符范围、全量模式的多字符对应与原生搜索语法保护仍待设计验证。
- 歧义处理优先召回：用户选择「尽量不漏搜」，接受 `发／發／髮` 对称互搜及其带来的不同含义结果。尚未确认切换精确搜索的产品入口。

## Unicode 等价与异体关系

来源：[Unicode UAX #15](https://www.unicode.org/reports/tr15/)，第 1 节对规范等价、兼容等价及 NFKC 的说明。Unicode 明确警告不应对任意文本盲目使用 NFKC/NFKD，因为可能抹去有意义的区别。

本地使用 Python `unicodedata`（Unicode 15.0.0）核验以下结果，属于数据语义检查，不是 Obsidian 集成验证：

| 输入 | NFKC 输出 | 说明 |
| --- | --- | --- |
| `⼀` U+2F00 | `一` U+4E00 | 康熙部首对应汉字 |
| `⼈` U+2F08 | `人` U+4EBA | 康熙部首对应汉字 |
| `､` U+FF64 | `、` U+3001 | 半角表意逗号 |
| `﹑` U+FE51 | `、` U+3001 | 小型表意逗号 |
| `，` U+FF0C | `,` U+002C | 全角逗号；与 `、` 不是同一兼容归一组 |
| `真` U+771F、`眞` U+771E | 分别保持原样 | 不能仅靠 Unicode normalization 互搜 |
| `①` U+2460 | `1` U+0031 | 全量兼容归一会额外合并圈号数字 |
| `Ａ` U+FF21 | `A` U+0041 | 全角拉丁字母 |

通常中文顿号和日语读点都可使用 `、` U+3001；字体外观不同不等于码位不同。若用户所指为另一对符号，需根据实际字符确认。

候选方向（未批准）：Unicode 官方等价数据补足编码变体，OpenCC 与经审核的汉字资料补足异体关系。不能把所有 Unihan 变体字段或所有外观相似字符不加区别地做传递合并；Unicode normalization 也不是自动涵盖全部汉字异体的方案。

仅归一化查询不能保证匹配未归一化的笔记内容；仍须验证原生搜索的查询展开或匹配入口，不能因此修改笔记或替换原始输入。

## 原生搜索接入：首轮静态核查

证据：通过 GitHub API 读取 [Obsidian 官方公开 API 类型文件](https://github.com/obsidianmd/obsidian-api/blob/master/obsidian.d.ts)，blob 为 `4fd05b81a95a7f2316f6ca9264abef45fd2c8d58`；只读检查本机 Obsidian 1.13.7 安装包的 `obsidian.asar` 中搜索相关代码。未启动或操控 Obsidian，未读取用户 vault，未修改应用。

- 公开 API 提供 `prepareSimpleSearch`／`prepareFuzzySearch` 字符串匹配助手及 `SearchComponent` 输入组件；本轮未找到原生全库搜索的公开查询改写／匹配替换钩子。这些助手本身不等于原生搜索引擎入口。
- 本机版本的全库搜索视图在 `startSearch()` 中读取输入，创建内部查询对象，随后通过原生队列读取文件、执行匹配并加入原生结果容器。
- `setQuery()` 会写回输入组件，因此不能直接用它提交展开查询而声称输入框始终保持原文。
- 查询对象包含原始查询、matcher 及 requiredInputs；视图还通过输入组件保存近期搜索、读取持久化状态。扩展实际匹配时不能污染这些原始查询状态。
- 内部查询和匹配对象提供潜在接入位置，但访问方式、时机、异步任务、多搜索视图、更新兼容及结果定位仍未运行验证。不能从静态源码推断已经可用。

初步判断：满足“保留原输入＋复用原生结果”很可能需要隔离使用未公开内部接口。拟在接口不兼容时关闭增强、提示原因并恢复原生搜索，不采用隐藏替换输入框文字或复制一套原生结果 UI 的方式冒充满足约束。此风险与降级行为需用户确认。

## 网页搜索与现有插件源码交叉核查

用户要求换用网页搜索工具后，使用 `web_search` 找到两个类似插件，再通过 GitHub API 读取作者仓库原始代码（仅参考分析，未安装、复制或采用第三方实现）：

| 插件与固定源码 | 实际实现 | 与本项目约束的差别 |
| --- | --- | --- |
| [CJK Cross-Script Search](https://github.com/sai1047976/obsidian-cjk-cross-search/blob/5fa8df99901e0b873f9709378df66eb6194d8067/src/patch/search-patcher.ts) | 修改内部 `SearchView.setQuery` 及输入组件 `changeCallback`；调用原方法提交展开查询后，仅在 typing reroute 路径把 `inputEl.value` 改回原文 | 并非从未改动输入值；普通程序调用路径没有同样的恢复分支。源码不足以证明满足所有原输入、选区、历史持久化要求，尚未实测 |
| [Unified Chinese-Characters Searcher](https://github.com/Yorkli1/Unified-Chinese-Characters-Searcher/blob/4e2a777f81a4041797576a9e7ac950ca5a72d9cf/src/search-hook.ts) | `_doExpand()` 直接将展开串写入 `input.value` 并触发原生 input／keydown 事件 | 会让输入框变成展开后的查询，不满足“始终显示原始输入” |

CJK Cross-Script Search 的 README 自身也明确承认依赖内部接口。上述证据支持原生查询展开方向可借鉴，但没有发现新的稳定公开接入 API，不能用插件介绍中的“保留原文”替代源码和运行验证。用户尚未回答是否接受内部接口与更新降级风险；不视为同意。

搜索另找到 [Obsidian Search 官方帮助](https://obsidian.md/help/plugins/search) 和[开放核心搜索 API 的论坛请求](https://forum.obsidian.md/t/add-the-search-from-the-core-plugin-to-the-obsidian-api/104011)。搜索摘要仅作发现线索；关键行为以上述官方类型定义、本机应用静态核查与固定插件源码为依据。

## 三端可行性判断与验证边界

用户补充：iOS 和 Android 都必须支持。直接读取 [Obsidian 官方 Mobile development 文档源码](https://github.com/obsidianmd/obsidian-developer-docs/blob/main/en/Plugins/Getting%20started/Mobile%20development.md)，确认移动端没有 Node.js／Electron API，且 JavaScript 特性支持受系统引擎版本影响；文档提供 Android WebView 与 iOS Web Inspector 真机调试方式。

工程判断（探针完成后更新）：已在 macOS / Obsidian 1.13.7 实测小字表内部匹配、原输入、原生列表、高亮、点击定位及禁用后下一次查询恢复。iOS／Android 按用户要求由用户测试，当前没有移动端通过证据；也没有其他桌面平台／版本兼容保证。

已验证的探针机制：保留输入组件和原始 query，在原生创建查询对象之后、开始扫描之前扩展内部 matcher 及相应输入需求，仍让原生扫描原文、生成命中范围并渲染结果。桌面 1.13.7 通过 `renderSearchInfo` 顶层调用处介入实测成功；该方法仍是内部接口，跨版本／跨平台一致性未验证，不作为承诺的固定接口，也不等于已批准正式插件架构。

三端约束：

- 运行时只用可在 WebView 运行的 JavaScript／TypeScript 产物、Obsidian API 和必要的内部适配；不使用 Node 原生 OpenCC 模块、系统命令或 Electron 专属能力。
- 字表在构建时处理并打包；构建工具可以用 Node／Python，但不要求手机安装它们。无需运行时联网获取字表。
- 不修改输入值来提交扩展查询；优先复用原生对笔记原文的匹配结果与偏移，避免归一化改变长度后造成高亮／跳转错位。
- 中文、日文、韩文 IME 组合输入、光标／选区、粘贴、清空、历史恢复和程序调用入口都需检查，不能只测键盘输入。
- 大字表展开、多字符兼容关系、长查询、取消旧搜索和手机性能需有明确测试，不采用整词变体的无界组合枚举。
- 桌面移动模拟可检查部分布局／分支，但不是 iOS／Android 的运行时验证；两端原生 Obsidian 都需要实际测试环境。
- 更新后内部接口不可用时的降级策略仍待用户确认；不存在对所有未来 Obsidian 版本的无维护兼容保证。

用户已批准并完成上述少量样例的桌面探针，未在真实笔记库部署。移动端由用户自行测试。完整字表、复杂查询语法、性能和正式架构仍需后续设计与验证。
