# CJK Search：完整字符数据接入设计

状态：本设计及实施计划均已获用户批准；主会话已完成实现、自审和 macOS / Obsidian 1.13.7 验证，已有测试库已更新至 0.1.0。实施清单位于 `../plans/2026-09-21-full-character-data.md`，实际证据与未验证范围见 [实现报告](../../research/full-character-data.md)。移动端仍由用户实测。

## 1. 目标与已确认行为

将四组样例替换为所选 Unicode／OpenCC 字符关系的完整版本化数据，使用户继续在 Obsidian 原生全库搜索框输入原文，由原生搜索显示结果、高亮并定位。

- 仅使用 Unicode 官方数据与 OpenCC 官方字符字典，不转换地区词汇，不翻译。
- 优先召回，默认对称互搜，包括 `发／發／髮`、`弁／瓣／辨／辯` 这类多义合并。
- 默认限定东亚文字及标点兼容；全量兼容开关默认关闭。
- 不改变搜索输入、近期历史或笔记，不建立另一套笔记索引。
- 保留可复制的诊断日志，不记录搜索原文、笔记内容或路径。
- 交付时更新现有独立测试库中的插件文件，不覆盖用户测试笔记。

“完整”指完整处理固定版本中本设计选定的关系，不代表所有上游字段、所有地区标准或所有历史汉字都已覆盖。

## 2. 选择与结构

采用**构建时处理官方数据，随插件打包生成字表**。不采用运行时下载／解析原始数据库，也不引入 OpenCC 原生运行时。

数据流：

```text
固定版本的官方文件 → 校验及解析 → 选取有类型的关系
→ 分组与兼容序列索引 → 离线数据产物
→ 纯查询展开函数 → 已验证的原生搜索适配层
```

构建工具与 Obsidian 运行时代码分开。构建可以使用本机 Node／Python；运行时只用 JavaScript 和 Obsidian，不依赖 Node、Electron 或联网服务。

保留现有探针作为回归基线；正式数据集成代码置于仓库根目录的 `src/`，构建工具置于 `scripts/`，官方输入、锁定信息及生成审计报告置于 `data/`。测试库路径保持不变。

## 3. 数据版本与许可

- Unicode：固定 **18.0.0**。采用 `Unihan.zip`、`UnicodeData.txt`、`EquivalentUnifiedIdeograph.txt` 及需要的同版本脚本／区块属性文件。
- OpenCC：固定官方 **ver.1.4.2**，提交 `025f371dc76b598d77384fbdab90c937471844d8`。2026-09-21 通过 GitHub API 核对该标签及目录。
- 导入前验证来源、版本头、预期字段、UTF-8、文件 SHA-256。建立锁定清单，后续离线重建必须与清单一致；不随 HEAD 自动变化。
- 若指定版本不可取得、内容变化或解析失败，停止构建并报告，不静默更换版本或跳过记录。
- 生成统计包含：每类输入／有效／排除关系数量、字符数、分组数、最大组、兼容序列数、文件体积、生成文件校验值。
- 保存关系的原始方向、字段、来源文件和码位，便于解释合并路径；运行时不必携带全部审计记录。
- 分发包含 Unicode License V3、OpenCC Apache-2.0 及上游要求的版权／NOTICE 声明。

## 4. 字符关系策略

### 默认纳入

| 来源 | 采用规则 |
| --- | --- |
| Unihan | `kSimplifiedVariant`、`kTraditionalVariant`、`kJapaneseNewVariant`、`kJapaneseOldVariant`、`kZVariant` 的全部有效关系 |
| OpenCC | `STCharacters.txt`、`TSCharacters.txt`、`TWVariants.txt`、`HKVariants.txt` 中的单码位键与单码位候选，保留所有候选，不只取首选 |
| OpenCC 日文表 | 对 `JPShinjitaiCharacters.txt` 做差异报告，仅补足 Unicode 日文关系未覆盖的字符关系 |
| 部首专表 | 只取康熙部首、CJK 补充部首对应，不自动纳入笔画；例如 `⺅／亻`，不自行推导 `亻／人` |
| UnicodeData | 按下节规则接入规范／兼容分解关系 |

所选单码位关系按对称连通分组用于搜索。允许这些明确选定关系之间传递合并，不允许其他字段充当连接边。生成完整组及来源路径报告，审核最大组和反例。

### 不自动纳入

- `kSpoofingVariant`、`kSpecializedSemanticVariant`。
- 未逐项审核的 `kSemanticVariant`：保留候选报告，本轮不将其作为新增合并依据。同一对字符若已由允许字段明确支持，不受影响。
- OpenCC 词组字典、词汇替换配置；字符字典中若出现非单码位项，明确报告并停止该导入的验收，不能悄悄截断或当成词汇收录。
- IVS／标准化变体序列的自动忽略；不删除变体选择符或改变 emoji。

若允许字段意外导致 `土／士`、`未／末`、`丼／井` 合并，验收失败：显示来源路径并重新审查，不能为了测试通过而静默删边。

## 5. 默认与全量兼容

### 默认东亚模式

纳入汉字兼容码位、部首、假名／谚文兼容形式，以及东亚标点的官方分解关系。根据同版本属性和明确区块筛选源字符，不凭字体外观判断。

源字符范围为 Han／Hiragana／Katakana／Hangul 脚本，以及这些补充区块中的相关分解记录：CJK Radicals Supplement、Kangxi Radicals、CJK Symbols and Punctuation、Enclosed CJK Letters and Months、CJK Compatibility、CJK Compatibility Forms、Vertical Forms、Small Form Variants、Halfwidth and Fullwidth Forms。

上述范围内，字母／数字兼容形式或分解到拉丁、希腊、西里尔字母及数字的单位缩写留给全量模式，不通过标点关系间接带入。单码位汉字的简繁与异体关系不受这个兼容筛选器限制。

### 全量兼容模式

开启后额外使用 UnicodeData 中其他字符的分解映射，包括 `①／1`、`²／2`、`Ａ／A`、`ﬃ／ffi`。递归分解和候选去重按固定数据完成，不能依赖手机宿主的 Unicode 版本。

“全量兼容”表示完整导入所选版本的字符分解映射，**不是声称实现完整 Unicode NFKC 算法**：不另外提供任意组合标记重排或算法性 Hangul 音节归一化。字符串匹配仍受本节规则和下一节查询边界限制。

### 多字符与非 BMP

- 单码位组与多码位分解序列分开存储，不能把序列塞进正则字符类。
- 多字符映射须双向匹配，例如 `㍿／株式会社`、`ﬃ／ffi`，并能与已纳入的汉字异体关系组合。
- 匹配序列不能只贪心选择最长候选而丢掉其他合法分段，也不能预先枚举整个查询的所有字形组合。
- 生成适用于原生正则引擎的分支；非 BMP 字符必须作为完整字符匹配，不假定原生正则一定启用 `u`，不允许只命中半个代理对。
- 保留输入和笔记原文，匹配范围始终对应原生文件的 UTF-16 偏移；不同长度分解必须验证高亮与点击定位。

## 6. 查询和原生集成边界

沿用已验证的时机：原生查询对象创建后、开始扫描前，在 `renderSearchInfo` 顶层调用处仅替换 matcher 和 requiredInputs。保留原始 query、输入和历史，原生负责文件扫描与结果展示。

本轮只增强普通连续字面文本。空白分词、原生操作符、引号、括号、正则、否定、文件／标签／属性过滤不在本轮解析；检测到后保持整条查询原生行为并输出跳过原因。不能先归一化查询，再把原文中的全角符号误解释成操作符。

无映射保持原生行为。内部接口缺失、数据校验失败或展开失败时，保留原生查询并输出可见诊断，不能清空查询或返回伪造的空结果。

初始保护上限：输入 256 个 Unicode 码位，展开正则 65,536 个 UTF-16 单元，展开过程 4,096 个分支节点。构造过程中逐步检查，不等指数枚举完成后才判断；超限整条回退原生并提示本次没有增强，禁止偷偷截掉候选。基准测试记录这些上限下的行为；若必须改变默认值，记录原因和测试证据。

开启／关闭兼容模式影响下一次搜索，设置说明明确提示重新输入查询；不宣称自动重算既有结果。保留 Obsidian 原生大小写设置。

## 7. 设置、日志与生命周期

仅新增一个原生 Obsidian 设置项：**全量兼容匹配**，默认关闭，持久化保存，附例子说明可能扩大结果。无需另造设置界面或引入 UI 库。

保留当前诊断命令和事件；日志增加数据版本、数据摘要、模式、展开耗时、回退原因。修正“四组样例”描述；默认不输出查询或内容。

适配层需检查接口和数据结构再安装；处理当前及后续打开的搜索面板，不重复包裹。卸载时清理自己的事件与包装，不覆盖其他插件后来安装的方法。无法确认兼容时回退并提示，不承诺支持所有其他搜索插件。

插件的暂用 ID 保持 `cjk-search-probe`，以便更新用户当前测试安装，不制造两个同时修改搜索的插件。显示名称／描述说明已是全量数据测试版，仍未正式发布；另行发布前再决定最终 ID。最低版本保持 1.13.7，不虚构更早版本兼容。

## 8. 验收

### 数据及纯逻辑

- 同一锁定输入重复构建得到相同数据与摘要，缺文件／坏校验和不能成功构建。
- 所有允许字段及字典记录都有纳入或明确排除的计数，不只测试几个手写字符。
- 每条纳入关系验证双向匹配；验证多候选、混合序列、补充平面字符和匹配边界。
- 代表正例：`体／體`、`真／眞`、`发／發／髮`、`国／國`、`弁／瓣／辨／辯／辩`、`⼈／人`、`⺅／亻`、`、／､／﹑`。
- 代表反例：`土／士`、`未／末`、`丼／井`、`鼠标／滑鼠`；`鼠标／鼠標` 应匹配。
- 默认不增加 `①／1`、`²／2`、`Ａ／A` 的等价匹配；开启后验证双向匹配及多字符兼容；关闭后恢复。
- 验证长度／分支上限、字面符号转义、原生语法跳过和数据损坏回退。

### 实际 Obsidian

复用独立 profile／合成库的桌面工具，不操作真实库。验证原输入、历史、实际输入事件、状态恢复、原文高亮、点击、禁用恢复和笔记未变；增加不同长度序列、非 BMP 字符、设置持久化及开关测试。

记录加载与查询展开耗时、数据体积和大查询回退行为，不以几条样例宣称大库性能或手机性能。

自动化之外，将通过验证的插件和许可证放进用户已有的 `manual-test-vault/.obsidian/plugins/cjk-search-probe/`，只替换明确的插件产物，保留现有设置及所有笔记。不得在 Obsidian 正在使用时主动卸载用户插件；提示用户关闭再启用。

macOS / Obsidian 1.13.7 为本轮自动化环境；手机由用户验证。Windows、Linux、其他版本或移动端没有实际证据时不标记通过。
